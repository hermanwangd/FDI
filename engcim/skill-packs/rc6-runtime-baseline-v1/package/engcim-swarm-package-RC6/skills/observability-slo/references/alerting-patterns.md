# 告警模式速查（Alerting Patterns）

## 症狀 vs 原因（分層）

```text
症狀層（會喚醒人）：SLO burn rate、可用性、端到端延遲、錯誤率（使用者視角）
原因層（進 dashboard / runbook）：CPU、記憶體、磁碟、queue 深度、GC、連線數
```

原因層指標只在「必然且即將導致症狀」時才告警（如磁碟依趨勢 4 小時內必滿）；
其餘情況它是**診斷資料**——症狀告警的 runbook 裡引用它，而不是讓它自己告警。

## 多視窗 burn rate 告警（推薦骨架）

| 告警 | 長視窗 | 短視窗 | 燃燒率閾值 | 嚴重度 |
|---|---|---|---|---|
| 快速燃燒 | 1h | 5m | ≥ 14.4（30d budget 2%/h） | SEV2，頁面 |
| 中速燃燒 | 6h | 30m | ≥ 6 | SEV2/3 |
| 慢速燃燒 | 3d | 6h | ≥ 1 | SEV3，工單 |

- **長視窗＋短視窗 AND**：短視窗確認「現在還在燒」，避免已恢復的舊事故重複告警。
- 閾值數字是骨架起點，按服務流量與容忍度調整；調整屬治理動作（人類批准）。

## 反模式（見到就改）

| 反模式 | 問題 | 改法 |
|---|---|---|
| 對原始計數告警（「錯誤 >100 次」） | 流量增長即誤報 | 改用錯誤率／burn rate |
| 每個原因指標都告警 | 告警海嘯、疲勞 | 原因層降為 dashboard＋runbook 診斷步驟 |
| 告警無 runbook 連結 | 收到者無所適從 | 補動作欄或刪除 |
| 閾值貼著日常波動 | 天天誤報 → 狼來了 | 以 baseline 的 p99 以上＋業務影響定閾值 |
| 靜音當處理 | 問題累積 | 靜音要有期限與 owner；噪音審查時檢討 |

## 噪音審查指標

- **有效行動率**＝觸發後有實際處置（非靜音、非「看一下沒事」）的比例。
- 有效行動率 < 30% 的告警：調閾值、改條件、或刪除——並在健康報告記錄結論。
- 零觸發超過一季的告警：驗證它還活著（Verifier 測試觸發），否則它是裝飾。
